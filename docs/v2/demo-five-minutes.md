# 五分钟讲解脚本

先按 [交付入口](delivery.md) 完成 `demo` 并启动页面。安装与自动化实验在讲解前完成；讲解展示实际保存的执行结果，明确指出记录时间，不把历史回放说成现场模型调用。

| 时间 | 操作与讲解 | 证据 |
|---|---|---|
| 0:00–0:45 | 说明业务问题：工单提交成功、响应丢失、盲目重试可能重复。区分被测 Agent、业务系统和验证平台。 | README、UPSTREAM |
| 0:45–1:45 | 页面运行 T03 / Scripted / unsafe，再运行 fixed，选择两次运行作对比。指出 2 张 FAIL 与 1 张 PASS、提交在故障之前、dedup_confirmed。 | 本次 business-api 报告、数据库观察与事件 |
| 1:45–2:30 | 展示 delivery.json 的 A/B/C 真网络实验；说明本地页面 T03 是函数级故障，而 controls 目录通过真实 MCP、HTTP 代理和独立提交确认断连。 | controls/independent-recheck.json |
| 2:30–3:30 | 恢复详情选择“业务提交后恢复”，对比执行完成、业务已确认、恢复次数与预算；再选 Gitea 缺少写入证据，说明为何保持待核实。 | 本次 recovery-index、CI 4 场景证据 |
| 3:30–4:15 | 展示 Gitea 是未修改的独立业务对象，以只读 API 确认 Issue，平台不声称掌握内部数据库提交或原子幂等。 | ci/public/summary.json；网络/恢复私有证据本机查看 |
| 4:15–5:00 | 展示已知重复候选被同一固定发布契约拒绝，以及 CI 历史红绿灯；说明本候选版的 CI 状态和独立试用状态。 | negative-gate；[历史索引](history.md)、[本轮交付](d35.md) |

结束时让观看者打开健康检查、下载本次报告，并用自己的话回答：“为什么调用两次可以正确，而创建两张工单不正确？”

边界：离线确定性执行不代表模型智能评测。D34 真实模型历史实验为 6 槽位、16 次请求；故障样本选择查询恢复，没有创建重试，因此不能据此宣称幂等修复提高模型成功率。独立试用未收到反馈前不宣称完成用户验证。
